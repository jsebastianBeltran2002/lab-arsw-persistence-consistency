# ADR-001 · Persistencia y garantías del tablero

- Equipo / integrantes: ARSW-EQP-03, Sara Arteaga, Johan Beltrán y Julián Tinjacá
- Estado: aceptado
- Fecha y commit: 31 de octubre de 2026, último commit del repositorio de entrega

## Contexto
El sistema es un tablero colaborativo con dos servicios. Gestión guarda usuarios, tableros y membresías en PostgreSQL. Contenido guarda el documento del tablero en MongoDB y usa Redis para la presencia y para una caché de permisos.

Las operaciones que tuvimos en cuenta son leer el tablero, que es la más frecuente y la que usa k6, editar el título enviando la versión esperada, revocar o conceder el permiso de edición, registrar y consultar presencia, y consultar el permiso desde la interfaz.

Los datos críticos son las membresías, porque deciden quién puede escribir, y el contenido, porque es el trabajo de los usuarios. La presencia y la caché son datos efímeros. La práctica usa una sola instancia de cada base, no tiene transacciones distribuidas y los usuarios se simulan con un header.

Al correr el baseline encontramos tres defectos. Dos ediciones con la misma versión devolvían 200 las dos y la versión pasaba de 1 a 3, o sea que se perdía un cambio. Luis podía escribir después de que le quitaron el permiso porque se usaba la caché. La presencia nunca expiraba. Además, con Redis caído la presencia respondía 503 y con Gestión caída se podía escribir usando el permiso que estaba en caché.

## Decisión
1. Motores. PostgreSQL es la fuente oficial de permisos. MongoDB guarda el tablero con las preferencias dentro del mismo documento. Redis guarda la presencia con TTL de 20 segundos y la caché de permisos de la interfaz con TTL de 60 segundos. El detalle está en la matriz.
2. Control optimista de versiones. En save_board la versión esperada va dentro del filtro del mismo find_one_and_update que cambia el título e incrementa la versión. MongoDB ejecuta esa operación de forma atómica sobre el documento, entonces si llegan dos escrituras con la misma versión solo una encuentra el documento. La otra recibe None y la API responde 409 para que el usuario recargue. Un 409 es una respuesta correcta del negocio, no una falla del servidor.
3. Permisos para escribir. permission_for_write siempre consulta a Gestión, que lee PostgreSQL. La caché de 60 segundos queda solo para la interfaz. Así, una escritura que empieza después de confirmar una revocación recibe 403. Si Gestión no responde se devuelve 503 y no se guarda nada, porque preferimos rechazar la escritura antes que aceptarla con un permiso viejo. No elegimos bajar el TTL porque solo reduce el problema, y tampoco invalidar la caché al revocar porque depende de que ese mensaje llegue y la caché seguiría sin ser la fuente oficial.
4. Presencia y degradación. touch_presence hace un solo SET con EX, de modo que el valor y la expiración se guardan juntos y cada heartbeat renueva el tiempo. Si Redis falla se captura solo RedisError y se devuelve False. El endpoint responde 200 con available en false y aumenta el contador de degradación. Editar no depende de Redis, solo de MongoDB y de Gestión.

## Alternativa considerada
Evaluamos guardar el contenido en PostgreSQL usando una columna JSONB. La edición sería un UPDATE con la condición de versión en el WHERE, dentro de una transacción que también lea la membresía con FOR SHARE. Tendría la misma garantía de versiones y además cerraría la ventana de revocación, porque permiso y escritura quedarían en la misma transacción. La descartamos para esta práctica porque obliga a migrar el servicio de Contenido, junta los dos servicios en un mismo esquema y MongoDB ya da la atomicidad que necesitamos para el control de versiones.

También pensamos en quitar Redis. La corrección no cambia porque la caché ya no autoriza, pero se pierde la presencia y cada consulta de permiso de la interfaz iría a PostgreSQL. Lo dejamos porque si Redis se cae solo se degrada la presencia.

## Consecuencias
- Cada escritura hace una llamada extra a Gestión y una consulta por llave primaria, que es barata. Las lecturas no cambian. El P95 de k6 fue 9,34 ms antes y 9,25 ms después, lo cual es casi igual porque k6 solo hace lecturas.
- Aparecen más respuestas 409 y el contador de conflictos sube. Ese es el precio de no perder ediciones, y el cliente tiene que recargar y volver a intentar.
- Fallas que se toleran: con Redis caído la edición sigue en 200 y la presencia responde 200 pero sin estar disponible.
- Fallas que bloquean a propósito: con Gestión o PostgreSQL caídos toda escritura da 503 aunque haya un permiso en caché. Con MongoDB caído no se puede leer ni escribir el tablero porque no hay réplica.
- Ventana entre validar y escribir. La validación ocurre en Gestión y la escritura en MongoDB, y no comparten transacción. Si la revocación se confirma justo después de validar y antes de guardar, esa escritura se acepta. La garantía solo cubre escrituras que empiezan después de la revocación. Para cerrarla se podría mover todo a PostgreSQL y validar y escribir en la misma transacción, o manejar un número de época de permisos que Gestión incremente al revocar y que Contenido incluya en el filtro atómico, o en último caso auditar y revertir las ediciones hechas después de la revocación.

## Historial creciente
El historial va en una colección aparte llamada board_history. Cada evento guarda el id del tablero, la versión, el usuario, la fecha y el cambio realizado. Se crea un índice único sobre id del tablero y versión descendente, lo que también evita duplicados si se reintenta una inserción.

Después de una edición exitosa se inserta el evento con la nueva versión. Si se quiere que nunca se pierda un evento, se puede usar una transacción de varios documentos, que requiere replica set, o una cola pendiente dentro del documento que un proceso vacía.

La consulta se pagina por cursor: se piden los 20 eventos con versión menor a la última que vio el usuario, ordenados de mayor a menor. Evitamos skip porque se vuelve más lento a medida que crece la colección. Los eventos antiguos se pueden archivar o borrar con un índice TTL según la política que se defina.

Meter el historial dentro del documento sin límite sería un problema porque el documento crecería hasta el máximo de 16 MB, cada lectura del tablero traería todo el historial, cada edición tendría que reescribir un documento cada vez más grande y no se podría paginar bien. Embeber solo tiene sentido para datos pequeños y acotados como las preferencias.

Lo que las pruebas no demuestran: no prueban el caso de una revocación que ocurre al mismo tiempo que una escritura en curso. Tampoco prueban replicación, consenso ni particiones de red, ya que cada base es una sola instancia y detener Redis es una falla de dependencia. La carga de k6 solo lee, así que no mide el costo de validar permisos con escrituras concurrentes, y 100 segundos con 5 usuarios no demuestran estabilidad sostenida.
