# ADR-001 · Persistencia y garantías del tablero

- Estado: **aceptado**
- Fecha y commit: 2026-10-31 · ver último commit del repositorio de entrega

## Contexto
Un tablero colaborativo con dos servicios: **Gestión** (usuarios, tableros, membresías en PostgreSQL) y **Contenido/colaboración** (documento del tablero en MongoDB, presencia y caché de permisos en Redis). Operaciones:

- Leer el tablero (pública en la demo, la más frecuente — es la que carga k6).
- Editar el título con `expected_version` (requiere permiso de edición).
- Revocar/conceder permiso de edición (Gestión).
- Heartbeat de presencia y consulta de presencia.
- Consulta de permiso para la UI.

Datos críticos: membresías (autorización) y contenido (trabajo del usuario). Datos efímeros: presencia y caché. Restricciones: instancias únicas (sin réplicas, sin transacciones distribuidas), identidades simuladas con header `X-User`, sin recarga automática del código.

El código base presentaba tres defectos (evidencia `entrega/evidencias/baseline-20261031T124847048088Z.json`): dos ediciones concurrentes con la misma versión ambas devolvían 200 (*lost update*, versión 1→3); Luis podía escribir tras ser revocado porque se usaba la caché (200, versión 2); la presencia nunca expiraba. Además Redis caído devolvía 503 en presencia y la autoridad caída permitía escribir con un permiso cacheado (200).

## Decisión
1. **Motores**: PostgreSQL = fuente autoritativa de permisos; MongoDB = documento del tablero con preferencias embebidas; Redis = presencia (TTL 20 s) y caché de permisos para la UI (TTL 60 s). Ver `MATRIZ.md`.
2. **Frontera de atomicidad / control optimista (TODO 1)**: `find_one_and_update({_id, version: expected_version}, {$set:{title}, $inc:{version:1}})`. La comparación y el incremento ocurren en la **misma operación de documento**, que MongoDB ejecuta de forma atómica; de dos escrituras con la misma versión solo una coincide con el filtro. La otra recibe `None` → **HTTP 409** ("recargue antes de editar"). Un 409 es un resultado de negocio correcto, no una falla del servidor.
3. **Política de caché y garantía de escritura (TODO 2)**: `permission_for_write` usa **siempre** `authoritative_permission` (Gestión → PostgreSQL). La caché de 60 s queda solo para la UI (`GET /permissions`). Garantía: *una escritura que comienza después de confirmada una revocación recibe 403*. Si Gestión no responde, el callback lanza 503 y la escritura **no se guarda** (*fail-closed*): preferimos rechazar a aceptar una concesión vieja. Descartamos acortar el TTL (solo reduce la ventana, no la elimina) e invalidar la caché al revocar (depende de que la invalidación llegue; sigue sin ser autoritativa).
4. **Degradación (TODO 3)**: `client.set(key, 'online', ex=ttl)` — valor y expiración en una única escritura, cada heartbeat renueva el TTL. Se captura **solo** `RedisError` y se retorna `False`: el endpoint responde 200 con `available:false` y aumenta `lab_degraded_total{feature="presence"}`. Redis es opcional para editar: la edición solo depende de MongoDB y Gestión.

## Alternativa considerada
**PostgreSQL con JSONB para el contenido** (un solo motor transaccional). El tablero sería `boards(id, doc jsonb, version int)` y la edición `UPDATE ... SET doc = jsonb_set(doc,'{title}',$t), version = version+1 WHERE id=$id AND version=$v` dentro de una transacción que también lea `memberships ... FOR SHARE`. Ventajas: misma garantía optimista y, sobre todo, **eliminaría la ventana de revocación** (permiso y escritura en una transacción). Se descartó para esta práctica porque: (a) exige migrar el servicio de Contenido y sus datos; (b) acopla Contenido al esquema de Gestión, rompiendo la separación de servicios; (c) MongoDB ya da atomicidad por documento suficiente para el control optimista.

También se evaluó **eliminar Redis**: la corrección no cambia (la caché no autoriza), pero se pierde la presencia efímera y cada consulta de permiso de la UI iría a PostgreSQL. Se mantuvo porque su caída ya está acotada a una degradación.

## Consecuencias
- **Costo**: cada escritura hace una llamada HTTP adicional a Gestión y una consulta SQL por PK (barata). Las lecturas —la carga dominante— no cambian: P95 k6 9,34 ms (base) vs 9,25 ms (solución), sin diferencia significativa porque k6 solo lee.
- **Más 409 visibles**: el contador de conflictos sube; es el costo de no perder ediciones. El cliente debe recargar y reintentar.
- **Fallas toleradas**: Redis caído → edición 200, presencia 200/degradada (`available:false`), caché de UI con *miss*/error y respaldo en Gestión.
- **Fallas que bloquean (deliberadamente)**: Gestión/PostgreSQL caídos → toda escritura 503 aunque exista permiso en caché. MongoDB caído → lectura y escritura 503 (es la fuente del contenido; no hay réplica).
- **Ventana entre validar y escribir (límite conocido)**: la validación (Gestión) y la escritura (Mongo) no comparten transacción. Si la revocación se confirma *después* de que `authoritative_permission` respondió `true` y *antes* de `find_one_and_update`, esa escritura se acepta. La garantía es solo para escrituras que **comienzan** tras la revocación confirmada. Alternativas para cerrarla: (1) mover contenido y membresías a PostgreSQL y validar+escribir en una transacción (`SELECT ... FOR SHARE`); (2) **época/versión de permisos**: Gestión incrementa `perm_epoch` en cada revocación, Contenido guarda en el documento la época vigente y la incluye en el filtro atómico (`{_id, version, perm_epoch}`), con Gestión empujando la nueva época a Contenido antes de confirmar la revocación; (3) auditoría y compensación posterior (revertir ediciones hechas tras la revocación).

## Historial creciente
Colección separada `board_history` en MongoDB:

```js
{ _id: ObjectId, board_id: "board-1", version: 7, user: "ana", at: ISODate, change: { title: { from: "...", to: "..." } } }
db.board_history.createIndex({ board_id: 1, version: -1 }, { unique: true })
```

- Escritura: tras un `find_one_and_update` exitoso se inserta el evento con la versión resultante (el índice único hace idempotentes los reintentos). Para no perder eventos ante una caída entre ambos pasos se puede usar una transacción multi-documento (requiere replica set) o un *outbox* embebido acotado que un proceso vacía.
- Consulta paginada por cursor (estable aunque lleguen nuevas versiones): `find({board_id, version: {$lt: ultimaVista}}).sort({version:-1}).limit(20)`; primera página sin `$lt`. Evitamos `skip` porque se degrada linealmente.
- Retención: archivado por antigüedad o índice TTL sobre `at` si la política lo permite.

**Por qué no embeberlo ilimitadamente**: el documento crecería sin límite hasta el máximo de 16 MB; cada lectura del tablero (la operación más frecuente, la de k6) transferiría todo el historial; cada edición reescribiría un documento cada vez más grande, aumentando latencia y memoria; y no se podría paginar ni indexar eficientemente. Embeber solo se justifica para datos acotados como `preferences`.
